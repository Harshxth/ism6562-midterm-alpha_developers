Task 1.3: Table Design Comparison (150–200 words)

The difference between the Cassandra orders_by_customer table and the PostgreSQL relational model centers on the trade-off between storage efficiency and read performance. In the PostgreSQL setup, the database follows normalization principles. I use foreign keys to link an order to a separate customers table, which eliminates data redundancy and ensures that updating a customer's state only happens in one place. However, this requires a JOIN operation at query time, which can become a bottleneck as data scales across multiple distributed servers.
In contrast, the Cassandra design utilizes denormalization to optimize for high velocity and low latency. I include customer_name and customer_state directly within the order row because Cassandra does not support relational JOINs efficiently. By duplicating this data, the system can fulfill a "My Orders" query with a single read from one partition. Furthermore, I created two separate tables, orders_by_customer and orders_by_product, to support specific access patterns. In a NoSQL environment, the schema is dictated by the query rather than the data relationships. Duplicating the data into these two structures allows the application to retrieve orders by customer or by product instantly without performing expensive table scans.
